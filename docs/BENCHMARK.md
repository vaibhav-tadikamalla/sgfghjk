# PeerGrid Benchmark System

## Overview

PeerGrid includes a production-quality benchmark system for measuring collaborative edit propagation latency, throughput, and CRDT convergence under load.

The system is inspired by the methodology in:
> Dang, Q.-V. & Ignat, C.-L. (2016). *Performance of real-time collaborative editors at large scale: user perspective.* In CCGRID '16.

## Quick Start

### Via Admin Dashboard

1. Open `/admin` → **Benchmark** tab
2. Enter target WebSocket URL (defaults to local server)
3. Set user count and duration
4. Click **▶ Start Benchmark**
5. Watch live p50/p95 update during the measurement phase
6. Results are persisted automatically — click any row in Run History to expand detail

### Via API (admin token required)

```bash
# Start a benchmark run
curl -X POST https://your-server/admin/benchmark/run \
  -H "Authorization: Bearer $ADMIN_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "userCount": 10,
    "durationSeconds": 60,
    "warmupSeconds": 15,
    "cooldownSeconds": 10,
    "typingSpeed": 2,
    "targetUrl": "wss://your-server/ws"
  }'

# Check status
curl https://your-server/admin/benchmark/status \
  -H "Authorization: Bearer $ADMIN_SECRET"

# List runs
curl https://your-server/admin/benchmark/runs \
  -H "Authorization: Bearer $ADMIN_SECRET"
```

### Academic Matrix (1–50 users)

```bash
curl -X POST https://your-server/admin/benchmark/matrix \
```

## Latency Measurement Methodology

### What Is Measured

**Collaborative edit propagation latency**: the time for an edit made by one simulated user to be received and applied by another simulated user.

### t₁ and t₂ Definition

```
t₁ = performance.now() captured in SimulatedEditor A
     immediately BEFORE Y.Doc.transact() is called

t₂ = performance.now() captured in SimulatedEditor B
     immediately AFTER Y.applyUpdate() returns when
     processing the broadcasted update from A

latency = t₂ - t₁ (milliseconds)
```

This measures the full path:
```
A: CRDT encode → WebSocket send
   → server receives
   → server broadcasts to all room subscribers
   → B: WebSocket receive → CRDT decode → Y.applyUpdate()
```

### Correlation Mechanism

Every Yjs update includes the originating `clientID` (a `uint32` generated by `Y.Doc`) and a logical clock in its binary header. The tracker uses `(clientID, clock)` as a correlation key:

1. Before `transact()`, sender captures `{clientID, clockBefore, t1}` → stored in pending map
2. Receiver calls `Y.decodeUpdate(update)` to extract `clientID` from the first struct
3. Tracker matches by `clientID:clock` → computes `latency = t2 - t1`

### Why This Is Valid

All simulated editors run in the **same Node.js event loop** as the PeerGrid server. `performance.now()` is monotonically increasing within a single process. No cross-machine clock synchronization is needed.

## Results Reference

All results are persisted in the `benchmark_runs` PostgreSQL table.

### Latency Statistics

| Field | Description |
|-------|-------------|
| `latency.sampleCount` | Number of successful t₁→t₂ measurements |
| `latency.minMs` | Minimum observed latency |
| `latency.meanMs` | Arithmetic mean |
| `latency.p50Ms` | 50th percentile (median) |
| `latency.p90Ms` | 90th percentile |
| `latency.p95Ms` | 95th percentile |
| `latency.p99Ms` | 99th percentile (tail) |
| `latency.maxMs` | Maximum observed latency |
| `latency.stddevMs` | Population standard deviation |

### Operation Statistics

| Field | Description |
|-------|-------------|
| `opsAttempted` | Total edits sent by all simulated editors |
| `opsPropagated` | Edits successfully received by a peer (= `sampleCount`) |
| `opsTimedOut` | Edits not received within 10s timeout |
| `successRate` | `opsPropagated / opsAttempted` |
| `propagatedOpsPerSec` | Throughput (propagated ops / measurement duration) |

### Convergence

After the cooldown phase, the system calls `Y.encodeStateAsUpdate(ydoc)` on every simulated editor and computes `SHA-256` of each result.

- `convergenceAchieved: true` — all editors' hashes are identical (byte-for-byte Yjs state equality)
- `convergenceAchieved: false` — at least one editor's state diverged

## Known Limitations

1. **Single-process only**: All simulated users run in the same Node.js process as the server. This means:
   - `performance.now()` comparisons are valid (monotonic within one process)
   - WAN latency is NOT measured
   - Results show CRDT+WebSocket overhead, not geographic network latency

2. **CPU/memory metrics are process-level**: `process.memoryUsage()` and `process.cpuUsage()` measure the entire PeerGrid server process, which also includes the benchmark runner itself.

3. **Throughput vs real users**: Real human users don't type in synchronized burst patterns. The benchmark uses random jitter (50%–150% of base interval) to approximate realistic timing.

4. **Max 200 concurrent users**: Enforced to protect Render free-tier memory (512 MB). Each `BenchmarkSimulatedEditor` holds a `Y.Doc` (~50–200 KB depending on content).

5. **Free-tier Render constraints**: The Render free tier may show higher latencies during cold starts and when the server idles. Run a small warmup manually before benchmarking deployed instances.

6. **Reconnect probability disabled by default**: Set `reconnectProbability > 0` to test reconnect resilience. Default is 0 to get clean baseline measurements.
